# 模型输入降噪研究

日期：2026-11-16。实现基准：eaddc41，验收记录：4c240f0。本轮未开始对局。

## 结论

P1/P2 已处理一部分机械重复，但尚不能称为完成了输入降噪。外部 MCP 的增量减少新增消息，不会删除客户端已有上下文；
API 回合间重建完整档案，目前把所有曾出现的官方说明积累后再次发送，后期输入仍可能增大。缓存、输入长度和决策质量需要分别测量。

下一步优先处理过期信息与重复表示，其次限制自动加载的知识范围，最后才考虑历史摘要或更激进的压缩。
保留全部对局原始记录，不等于每次推理必须重发全部原始记录。既有“保留整局所有回合”的设计不必因此改变。

## 数据与方法

读取四份既有 steps.jsonl，共 161 次带 prompt 的决策、49 次备战开场。三份来自 Claude 会话保存的旧日志，
20261116-153732 来自 Windows 已结束的旧对局。它们不是四份完整独立的通关实验，不用来计算胜率。

统计工具：scripts/analyze_prompt_inputs.py。对给定日志只读分析，不发模型请求、不发送键鼠。示例：

```bash
uv run python scripts/analyze_prompt_inputs.py runs/<对局目录> --output local/input-metrics.json
```

字符数均为 Python len，不是 token；开场平均值不包括系统提示词、工具定义、图片，以及回合内累计重发的消息。
“条目重复比例”仅对以 `- [类别]` 开头的完整首行精确去重，跨行的续行不计，不能等同于整个说明块的可删除比例。

在一张已有商店全图上重新跑 OCR，43 个文字框的原坐标列表为 769 字符；当前 27 个标号的对照表为 193 字符。
这是单张截图的表示差异，不是总输入减少 75%，也没有证明识别或决策更准确。

## 已完成的改善

- 条目真正入档后再标记已描述，避免“去重”误删信息。
- 备战操作说明集中在 system；攻略候选只在已有检查点提供；经验检索也移到检查点。
- 外部 agent 新回合接收增量，snapshot 可以恢复完整档案。
- 备战截图和标号替代整屏 OCR 坐标表；原始 OCR、原图和实际请求仍可追溯。
- 模型指出识别冲突时记录 perception_issues；行动值骤降不再强行记成已确认阵亡。

这些改动解决了部分重复、遗漏和错误确定性；尚未验证它们对实机胜率的影响。

## 仍存在的问题

### 1. 知识档案累计不等于按需提供

ScreenAgent 会把整局遇到的条目放进 RunLedger.entries，API 开场通过 render 把所有条目重新发出。
即使某个角色只在很早的商店出现过，随后既没买也不在计划里，它的说明仍占据后续每个回合的输入。

本地把四段历史 OCR、棋盘、原历史块和原当前状态交给当前序列化器重建，API 的备战开场平均约 1.46～1.58 万字符，
外部增量约 0.39～0.49 万字符；旧值约 1.18～1.38 万字符。
这是近似重建：检查点用历史节点近似，未重新分类全部旧事实，原状态含旧布局，补入了当前版本知识与局面要点，
也未包含图片 token、system 或完整客户端上下文。因此只用于发现“API 输入可能反增”的风险，不作为版本间节省率或质量对照。

建议：档案保留全部条目；推理时只自动加载当前棋盘、商店、装备、已生效修正及计划直接引用的知识。
不在当前集合的说明可通过按名称查询取回。不要用盲目的统一截字替代检索。

### 2. 外部增量仍有重复交付

已复现：一个条目在回合内 observation 首次出现时被发送并入档，但 delivered 游标未同步前移，下个回合开场
又通过 render_delta 发送一次。另一个风险是 render_delta 在实际模型调用前推进游标，输出过程应有明确的交付提交时机。

此外，render_delta 每次都会附完整 render_state，包含整篇已选攻略、装备记录和全部模型笔记。稳定的攻略仍被反复追加
到外部客户端上下文。建议对状态按字段版本交付，首次或 snapshot 提供完整值，之后只发变化。

### 3. 当前事实重复表示，且缺少来源与失效范围

perceive 已有 HUD、阵容、商店、装备，又追加局面要点中的经济、人数、同名角色、方向分类；另有档案里的装备记录。
棋盘文字还为每个格子重复坐标，而语义动作和截图标号已经能定位。不是所有重复都有害：截图和关键数字互相校验有价值，
但同一个程序计算出的值换三种说法，不构成三个独立证据。

更严重的是 ledger.equipped 只有追加，没有角色实例标识、卸下、出售、合成后的失效维护。代码虽然附“可能不准”，
仍把它放在当前状态；相同装备还能重复追加。应优先撤销或标记具体过期字段，而不是让模型自行判断整块可信度。

经济推算还依赖固定利息档、每次经验值及金币成本。规则修正可能改变这些值，应写明基准规则或使用当局有效参数；
无法确认就保留原始金币、经验读数，不把推算包装成确定事实。

建议当前局面只保留一份主表示：关键数字、占用格子与星级、商店及价格、装备道具、有效修正和新出现的错误。
派生信息只补主表示中没有直接给出的关系，例如买入后可升星。认不出的格子和缺失读数必须显式保留。

### 4. 模型笔记可能成为长期错误前提

旧 Haiku 对局 45 次决策只在第 15 步更新一次 run_notes。到了 2-4，笔记仍写“4 级起步、主 C 暂定流萤、
银狼没出现就不硬凑”，而后续执行记录已经出现 2 星银狼上场。它与当前攻略和当前阵容并列，形成多份不一致的方向。

建议程序只添加笔记的写入节点和当前节点，指出“自某节点以来未更新”；不擅自替模型改计划。
检查点要求模型明确保留或修订当前计划；即时战术仍由模型决定，不把旧计划升级为必须执行的规则。

### 5. 历史摘要与操作流水混在一起

close_episode 把最多 300 字操作、阵容、进场数字、模型小结拼成一条，再由 RunLedger.add 整条截到 600 字。
已复现：前面的操作和阵容足够长时，尾部的小结会消失。历史还保留点击坐标、失败重试等低层细节。
这属于信息丢失与噪音同时存在，不能仅靠更短的字符上限解决。

建议先分字段保存节点结果、关键状态变化、未解决错误、模型小结，再按优先级渲染；原始操作流水留在 steps.jsonl。
保留每回合记录，后续需要按位面折叠时仍能完整检索。

### 6. 截图与标号也会产生噪音

当前一个 API 回合保留全部对话图片，多轮刷新和 inspect 后会累积旧截图；外部 Codex/Claude 则由客户端维护图片历史，
服务端只能控制新发的内容，不能声称已清掉旧图。只保留最新图可能降低比较操作前后的能力，还会改变缓存前缀。

建议对 API 比较三种策略：回合全部图、当前图加上一轮图、当前图加按需局部图。先测读取当前数字、识别上一步变化、
标号选择是否受影响。外部 agent 先减少重复整屏观察，必要时由客户端压缩；不要混用两条路径的结论。

现在非备战界面给几乎每行 OCR 文字都编号；长描述和无关文字会覆盖画面，登录页也出现过字母残片标号。
建议优先编号按钮、卡片和格子，描述文字不逐行覆盖；保留原图或局部查看入口。

### 7. system 仍包含过时或重复的协议说明

system 写“回合结束后对话不保留”，对内部 API 成立，对外部 agent 不成立；还写“程序每一轮都会打开商店”，
实际是新备战回合固定流程之后打开。规则卡的备战操作部分约 1,734 字符，和操作协议仍有交叠。

这些内容应按真实执行行为修订。打法原则也存在具体语义风险：“5级搜牌”和“速升9级”目前合并成了相似的
“到等级前优先买经验”表述，两种标签是否应采用同一经济解释不能由降噪顺便决定。
应该把规则、维护者经验、攻略作者意见、程序推测明确分开，而不是把全部建议删掉或全部当成事实。

### 8. 缓存边界不是语义去重

事实、经历分别只追加，但它们拼成“事实→经历→条目”以后，新增事实会移动旧经历，新增经历会移动条目。
本地最小样例中，新增事实后首个差异在第 48 字符，而旧缓存标记在第 93 字符；这只能证明共同前缀发生变化，
不能据此计算真实 token 命中量，更不代表 system 的缓存必然失效。

实际应以厂商返回的 usage 和延迟衡量。不能为了保住缓存而无限保留不相关内容，也不能把“只入档一次”
表述为“模型只看一次”。

## 建议的下一阶段

本轮研究不继续改变运行时策略，避免把尚未验证的假设混进已提交的 P1/P2。建议按以下次序实施：

1. 修复可确定的信息错误：条目交付游标、过期装备、笔记时间、摘要截断、API/外部协议描述。
2. 合并当前局面的重复表示，移除已可语义定位的坐标；错误和缺失读数保留。
3. API 使用相关知识工作集，提供按名称检索；外部 MCP 对攻略、笔记等按版本发变化，snapshot 仍能恢复完整档案。
4. 离线比较图片历史和规则卡范围，再决定是否加入位面摘要。

建议的对照组：A=当前提交；B=只修过期/重复/交付；C=B+相关知识工作集；D=C+图片历史策略。
固定同一模型、同一截图与已核对状态，不执行游戏动作。每组至少覆盖商店、光环、选择弹窗、操作失败与规则修正场景。

主要指标：金币/血量/等级读取、角色格子与星级、当前修正召回、上一动作是否成功、标号目标是否正确、合法动作率、
过期事实引用率、历史问题检索与 snapshot 恢复。成本指标：完整请求 token、图片数量、usage、缓存读取、延迟。
不以更短的 prompt、更高的刷新次数或更少的调用次数替代质量验收。

## 外部依据与适用范围

- [Anthropic：Effective context engineering for AI agents](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)：
  讨论高信号上下文、按需检索、工具反馈与长期任务的压缩。支持把上下文视为需要管理的资源，不证明本项目使用某种模板就能提高胜率。
- [Anthropic：Writing effective tools for AI agents](https://www.anthropic.com/research/writing-tools-for-agents)：
  强调返回有意义的相关信息，并通过评测选择工具设计。可用于设计按名称查询和紧凑观察，不应照搬成更多工具总是更好。
- [OpenAI：Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)：
  缓存复用前缀的计算状态，输入仍参与输出生成；实际命中依赖请求边界和设置。它解决成本和延迟的一部分，不会自动删除语义噪音。
- [Liu 等：Lost in the Middle](https://arxiv.org/abs/2307.03172)，2023/2024：
  在问答与键值检索任务上观察到信息位置的影响。可用于设计本项目的位置对照实验，不能直接外推为 2026 年所选模型的游戏决策效果。
