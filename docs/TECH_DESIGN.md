## 1. 项目概述

### 1.1 目标

做一个由 LLM 自主游玩《崩坏:星穹铁道》常驻玩法「货币战争」S2 赛季「入画奇航」的 agent。三个诉求同等重要:

1. **好玩**:能看到模型每一步在想什么、为什么这么做;
2. **尽量高胜率**:从最低难度稳定通关开始,逐级提高难度;
3. **可对比模型**:任意能看图的模型都能接入,同一批局面下能并排比较不同模型的思考和决策(2026-11-16 起决策输入带截图,见第 20 节)。

### 1.2 非目标

- 不读游戏内存、不解析封包,只做"看屏幕 + 动键鼠"的外部自动化;
- 不做强化学习训练(没有模拟器);
- 不做多账号并发、打金等功能;
- 不做"副驾模式"(只给建议、人来点),首个可用形态就是全自动。

### 1.3 运行形态

- **运行环境**:Windows PC + 星穹铁道 PC 客户端(国服,简体中文),1920x1080 窗口模式,关闭 HDR,放在主显示器;对局期间键鼠被 agent 占用。agent 作为一个服务运行在这台 Windows 上,像 March7thAssistant 一样直接定位游戏窗口截图、发送键鼠,不经过任何中转。
- **开发方式**:代码可以在其他电脑上编辑,推送后在 Windows 上 `git pull`,再通过 SSH 运行和调试(注意事项见第 16 节)。
- **玩法特性**:自走棋类玩法,战斗自动进行,agent 只在备战、三选一等阶段决策。备战阶段是否有倒计时待核实;设计上按"单次决策允许十秒级延迟"处理。
- **观战**:Windows 被占用,所以网页界面要能在局域网内的另一台设备(电脑 / 手机)上打开。

### 1.4 合规与风险

第三方自动化违反米哈游用户协议,有封号风险,建议用小号。README 里要写明这一点。所用米游社接口是网页自身调用的非官方公开接口,必须低频访问(见 3.1.3)。

### 1.5 许可

GPL-3.0-only。这样可以直接参考或移植 March7thAssistant(GPL-3.0)的界面流程、区域坐标、卡死恢复逻辑。拷入代码时保留原版权声明;仓库根目录放 `LICENSE` 和 `NOTICE`。

### 1.6 已定的设计决策

以下是和用户确认过的,不要改:

| 议题 | 决定 | 原因 |
|---|---|---|
| 语言 | 后端 Python | OCR、截图、键鼠库都在 Python 生态 |
| 感知 | **截图为主,OCR + 模板匹配为辅**(2026-11-16 维护者改):决策模型直接看带程序标号的截图;OCR 和模板负责界面分类与规则处理、读数字、名字链接知识库、算局面要点、给点击坐标。只接入能看图的模型 | 纯文字时模型看不到局面:前台只站一人、弹窗盖住、界面错判、商店没读到都发现不了(第 20.1 节);原来是「OCR + 模板,不用视觉大模型,非视觉模型也能对比」 |
| 攻略的角色 | 攻略只给大方向和玩法指导;过渡阵容、装备选择、升本、D 牌(刷新商店)时机由模型自己判断。默认固定一篇作方向,只在战略检查点比较、改选(2026-11-16,第 20.5 节) | 用户想看模型自己思考,而不是照抄脚本;每回合重新排攻略会让模型反复改方向 |
| 程序与模型的分工(2026-11-16 加) | 程序只给事实和限制,不给打法建议;打法原则集中写在一处,由维护者审定;界面操作由程序包办,失败时重试或暂停,不占模型的决策轮数 | 第 20.1 节:建议分散重复、互相拉扯,模型一半的操作在替程序收拾界面 |
| 决策粒度 | 语义原子动作为主,加少量宏 | 思考过程有看头,同时控制调用次数 |
| 模型接入 | 统一用 URL + API key 直连 HTTP,不集成厂商 SDK;同时支持 OpenAI 格式和 Anthropic 格式 | 用户要自由换模型和网关 |
| 外部 agent 接入(2026-11-14 加) | 本服务提供 MCP 端点,用户自己的 agent 工具(DSH、Claude Code、Codex 等)连上来下棋,用的是这些工具自己的模型和额度;本服务不调用它们的命令行、不读取它们的登录凭据。先适配 DSH | 用户想用订阅额度;MCP 是通用协议,不锁厂商(11.9) |
| 前端 | 独立网页应用,用 ARC UI 组件库 | 用户指定 |
| 首个形态 | 全自动对局 | 用户指定 |

## 2. 玩法建模(S2)

### 2.1 玩法速览

玩家用金币在商店招募角色组建队伍,经过 3 个位面的一系列节点,每个节点自动战斗,击败最终首领即通关。

**已实测**(来自官方接口数据,见第 3 节):

- 角色费用为 1 / 2 / 3 / 4 / 5 费,另有 7 费的「星神★阿哈」(同名角色在数据中有 4 / 5 / 7 费三个形态);
- 角色分前台(Front)、后台(Back)、前后台通用(Common)三种站位类型,前后台技能不同;
- 角色有 1–3 星,技能描述按星级给出;
- 羁绊 34 个,分四类:阵营(12)、流派(11)、专属(6)、特殊(5);羁绊按上阵人数分档激活,例如「连击」为 2 / 4 / 6 / 8 人四档;
- 装备可合成,数据中有 105 件,类别为:进阶装备、特权装备、星徽、餐品改件、列车改件、宝钻、固有装备;简易装备两两合成进阶装备;
- 投资策略(对局中的三选一增益)298 条,三档品质;
- 投资环境 73 条(开局选择,影响整局);
- **主角光环**(S2 新机制)82 条:为某个上阵角色选择一个强化效果,每条带标签和适用角色列表。

**待核实**(第三方攻略或 S1 资料,数字不可直接使用):

- 小队生命初始 100,战斗未在行动值限制内清场会扣血,归零则对局结束;
- 上阵人数上限 = 等级 + 财富宝钻数;前台 4 格,后台 6 格 + 佩佩 / 叽米数 + 宝钻数(最多 9 格)(M7A,S1 资料;实机见过后台 6 格和 7 格,`vision/board.py` 按界面数字推格子数、按画面核对奇偶);备战席格数;
- 每个角色最多 3 件装备;
- 三个同名同星角色自动合成升一星;
- 存金币有利息且有上限,连胜有额外金币;
- 「奇遇」(S2 新机制):开局随机一个奇遇伙伴,影响整局,据称共 11 个、分装备 / 资源 / 节点三类。**官方接口里没有奇遇数据(2026-11-14 实测)**,只能从游戏内采集。用户告知的例子:「三月兔」会把奖励节点变为「幕后茶歇」,「不死狼」会在局内出现「委托」(见 2.3);
- 主角光环在位面 1、位面 2 的首领前各选一次;
- 阿哈通过收集和「欢愉」/「幻月游戏」羁绊升到 7 费,届时会改变商店内容;
- 通关时按剩余生命值提升职级(S1 规则:≥70 升 3 级,≥40 升 2 级,否则 1 级),失败不掉级;
- 有「标准博弈」和耗时更短的「超频博弈」两种模式,据称超频博弈没有利息;
- 商店各费用出现概率随等级变化(S1 时期的概率表见附录 C)。

### 2.2 对局流程与决策点

```
主页 → 选模式(标准/超频) → 选难度 → 开始对局
  → 投资环境选择 → 奇遇伙伴揭示
  → [ 进入节点(战斗 / 遭遇 / 首领 / 奖励 / 幕后茶歇 / …)
      → 备战阶段 → 自动战斗 → 结果 → 补给 / 投资策略三选一 / 委托 / 其他事件 ] × N
       └ 首领前:主角光环选择(待核实)
  → 通关或失败 → 结算、领奖
```

上图只是常见形态。节点的类型、数量和顺序,以及中间出现哪些事件,都会被投资环境、投资策略和奇遇伙伴改变(见 2.3),所以程序里不能写死任何一种流程。

| 编号 | 决策点 | 频率 | 决策方 |
|---|---|---|---|
| D1 | 模式与难度 | 每局 1 次 | 配置 |
| D2 | 投资环境选择 | 每局 1 次 | LLM(选择类) |
| D3 | 对局方向制定 / 调整 | 每局 1 次 + 触发式 | LLM(战略层) |
| D4 | 商店:买、卖、刷新、买经验 | 每个备战阶段多次 | LLM(战术层) |
| D5 | 站位:前台 / 后台 / 备战席移动 | 每个备战阶段 | LLM(战术层) |
| D6 | 装备合成与穿戴 | 每个备战阶段 | LLM(战术层) |
| D7 | 投资策略三选一 | 对局中多次 | LLM(选择类) |
| D8 | 补给选择 | 对局中数次 | LLM(选择类) |
| D9 | 主角光环选择(选角色 + 选效果) | 每局约 2 次 | LLM(选择类) |
| D10 | 放弃 / 重开 | 触发式 | 规则 + 战略层 |
| D11 | 继续、跳过、领奖、已知弹窗 | 高频 | 规则(反射层) |
| D12 | 奇遇伙伴带来的专属交互(幕后茶歇、委托等)和其他未专门处理的事件 | 视伙伴与策略而定 | LLM(通用事件处理,见 10.2) |

S1 的「专家顾问」交互:S2 接口中所有角色 `is_expert` 均为 false,先不做,待核实后决定是否彻底删除。

### 2.3 规则修正与流程变化

一局的规则不是固定的。以下来源都会在局内改变规则,统称**规则修正(modifier)**:

| 来源 | 例子 | 改变的东西 |
|---|---|---|
| 投资环境 | 「轮岗」:备战阶段开始时,使一个随机费用的刷新概率翻倍,每个备战阶段重新随机(已实测) | 商店概率,且每个备战阶段都在变 |
| 投资环境 | 「战争边疆」:第三位面的所有战斗节点都替换为遭遇节点(已实测) | 节点结构 |
| 奇遇伙伴 | 「三月兔」:奖励节点变为「幕后茶歇」(用户告知) | 节点结构 + 新界面 |
| 奇遇伙伴 | 「不死狼」:局内出现「委托」(用户告知) | 新的交互和局内目标 |
| 投资策略 | 298 条中约 90 条涉及节点 / 位面,约 100 条涉及金币 / 经验 / 连胜,约 50 条涉及商店 / 概率 / 刷新(按描述关键词粗略统计) | 节点、经济、商店 |
| 怪物词条(敌人词缀) | A8 起每局有 4 个;如「能量逃逸」让依靠能量施放终结技的主 C 很难打,特殊能量不受影响(维护者告知) | 阵容选择、主 C 选择、装备方向 |
| 羁绊 / 角色 | 开拓银轨的专属商店、奇兽花园的奇美拉、克拉拉每隔几个节点的改装、阿哈升到 7 费后改变商店 | 新界面、商店内容 |

由此得出的设计原则(在第 6、7、8、10 节落实):

0. **难度从 A8-1 起**:A8 以下没有怪物词条,不具参考性;开发、调试和评测都用标准博弈 A8-1 及以上,不玩超频博弈(维护者要求)。
1. **流程由画面驱动,不写死**:编排层每一步都看当前画面决定做什么,不假设位面数、节点数、节点顺序、是否有首领节点、三选一出现几次。节点类型从画面读取。
2. **新界面能被兜住**:常见界面有专门的处理器;其余可交互的界面交给通用事件处理(10.2),由模型根据画面文字和选项决定;实在无法识别时暂停并报警,保存截图以便补处理器。
3. **规则修正进入模型视野**:本局生效的所有规则修正(投资环境、奇遇伙伴、已拿的投资策略、主角光环,以及带特殊机制的羁绊)连同官方描述原文,作为提示词里单独的一段放在最前面;投资环境和奇遇伙伴都确定之后才制定对局方向;拿到会改变流程的修正后触发重规划。
4. **局内目标单独跟踪**:委托一类的局内任务,把要求、进度、奖励读进状态(`objectives`),让模型决策时能看到并主动去完成。
5. **不写死概率计算**:商店概率、节点构成都可能被修正,程序里不做依赖固定概率表的计算;宏(如 `roll_until`)只按每次刷新后实际看到的商店行动。
6. **奇遇伙伴边玩边完善**:官方接口没有奇遇数据,伙伴数量多,维护者也没有全部解锁,无法事先采集完整列表。所以:
   - 决策不依赖事先准备的伙伴数据:开局揭示伙伴时,感知层读出界面上的名称和描述,直接作为规则修正交给模型;
   - 每遇到一个伙伴,自动记进本机的伙伴档案 `data/companions.local.yaml`(名称、描述、首次 / 最近遇到时间、次数、截图);
   - 伙伴带来的流程影响(新节点、新界面、委托等)通过局内笔记和局后复盘沉淀为记忆(5.4);
   - 核对过的伙伴用 `cwagent companions export` 导出到随仓库发布的 `knowledge/companions.yaml`。

### 5.3 规则卡

`knowledge/rules.md`,手写,约 1–2k token,常驻系统提示词。内容:对局流程、经济规则、扣血、升星、站位与赋能、装备合成规则、S2 新机制(奇遇、主角光环、阿哈)、通用运营原则。

**所有数值必须来自用户游戏内核实**。未核实的条目在文件里用「【待核实】」标出,并且不注入提示词(加载时过滤掉带该标记的行),以免模型按错误数字决策。

### 5.4 记忆系统

官方描述只告诉模型「这个东西是什么」,很多决定胜负的知识不在里面:隐藏规则、打法技巧、踩过的坑。记忆系统让这些知识能被写下来、在合适的时候想起来、并随对局逐步修正。

**例子**(维护者提供,也是初始的种子记忆):

- 「经济严重过热」把全部奖励节点换成超级次元扑满,扑满跑得很快。普通奖励节点随便上几个角色就行,扑满节点却要有一定战力去「抓猪」,输出不足(例如只上 1 费角色)会让扑满逃跑、损失战利品。
- 绯英施放终结技时永久提高伤害增幅(官方描述)。奖励节点的战斗不限行动值、阵亡可无限复活(维护者告知,待核实),所以可以让绯英在奖励节点单独上场、刻意压低伤害,拖长战斗多放终结技来叠层。

**三类记忆**:

| 类别 | 内容 | 例子 |
|---|---|---|
| 机制 | 官方描述没写清楚的规则 | 奖励节点不限行动值、可无限复活 |
| 打法 | 在什么条件下该怎么做 | 绯英去奖励节点叠层;扑满节点要上有输出的阵容 |
| 教训 | 从失败中总结出的「不要这样做」 | 扑满局只上 1 费角色,扑满全跑了 |

**一条记忆的结构**:

```yaml
id: m-…
kind: 打法                      # 机制 | 打法 | 教训
title: 超级次元扑满需要有战力的阵容去抓
content: …                      # 写给模型看的完整说明,包括条件、做法和原因
triggers:                       # 什么时候想起这条
  entities: [经济严重过热, 次元扑满]   # 局面里出现这些名字时(规则修正、奇遇、商店、场上、选项、节点名、事件文字)
  nodes: [reward]               # 当前或下一个节点的类型
  screens: [environment_choice] # 当前界面
scope: [选择, 战术]              # 注入哪些决策层:战略 / 战术 / 选择 / 事件;空表示都可以
status: approved                # draft 待审核 | approved 已采纳 | rejected 驳回 | archived 不再使用
confidence: medium              # high 已核实 | medium 有依据未核实 | low 推测
source: 维护者                   # 维护者 | 局内笔记 | 复盘 | 攻略(附链接)
evidence: []                    # 支持这条记忆的对局与步骤,如 run-20261114-1/step-37
stats: {injected: 0, helped: 0, hurt: 0}
```

**存放**:

- `knowledge/memories.yaml`:随仓库发布的公共记忆,人工整理、经过核对,任何用户都能直接受益;
- `data/memory.sqlite`:本机在对局中学到的记忆(不入库)。同一个 id 两处都有时以本机为准。验证有效的本机记忆可以用 `cwagent memory export` 导出到公共文件,再提交到仓库。

**想起来(检索)**:不用向量检索。每个决策点从局面里收集「线索」:所有出现的名字(规则修正、奇遇伙伴、投资环境、已拿的投资策略、主角光环、场上和商店的角色、装备、三选一选项、节点名、事件文字)、当前和下一个节点的类型、当前界面、决策层。按触发条件命中的多少打分(名字命中权重最高),再按置信度和采纳状态排序,取前几条(默认 6 条、约 1500 字以内)放进提示词。没有触发条件的记忆视为通用记忆,参与所有决策点的排序但分数最低。`draft` 状态的记忆默认不注入(可在设置里打开,用于验证新记忆)。

**写下来**,三个入口:

1. **维护者手写**:编辑 `knowledge/memories.yaml`,或在网页「知识库 → 记忆」里添加,或 `cwagent memory add`;
2. **局内笔记**:决策工具的输出里有一个可选字段 `notes`,模型发现值得记住的规律时写下(如「这个扑满在 3 回合后逃跑了,当时只上了 1 费角色」),存为 `draft`,自动附上对局 id、步骤和截图;
3. **局后复盘**:每局结束后,复盘模型读本局摘要(节点序列、血量和经济曲线、关键决策与理由、局内笔记、本局注入过哪些记忆及之后的结果),输出对记忆库的操作:新增、修改(与已有记忆合并,不重复)、给本局用过的记忆投票(有帮助 / 有害)、建议归档。结果都是 `draft` 或投票,由维护者在网页审核;设置里可以打开自动采纳。

**修正**:每条记忆累计注入次数和有帮助 / 有害的票数。有害票明显多于有帮助票的记忆在网页上标红,提示维护者修改或归档。

**对比实验**:设置 `use_memories: true|false`,关闭后不注入任何记忆,用于比较记忆系统的效果,和 `use_guides` 一样。

**对其他部分的要求**:像绯英叠层这类打法要求 agent 在备战时就知道下一个节点的类型和规则,所以 GameState 要包含当前 / 下一个节点的类型(第 7 节),规则卡要写明各类节点的特殊规则(核实后),动作空间要能把角色移下场(已有 `move`)。

### 5.5 检索

不使用向量库。三种确定性检索:

1. **实体链接**:GameState 中出现的每个名字(商店角色、场上角色、持有装备、三选一选项、主角光环候选、当前投资环境、已拿的投资策略、当前奇遇伙伴)→ 查库,把描述原文附进提示词。场上角色附当前站位和星级对应的技能描述;商店角色附费用、羁绊、站位类型和简述。
2. **羁绊状态**:根据场上角色计算每个相关羁绊的当前人数、已激活档位、下一档还差几人及其效果。
3. **指引卡打分**(战略层用):

```
score = w1·log(1+use_count) + w2·support_hard(高难时)
      + w3·env_match(当前投资环境 ∈ card.environments)
      + w4·overlap(当前已有角色 ∪ 商店角色, card 的 carries 和 final_board)
      + w5·spotlight/companion 相关性(可先置 0)
```

取前 3–5 张。权重放配置里。

**现在的实现**(`knowledge/guides.py` + `Runner.guide_advice`,维护者要求动态选攻略):每个备战回合按场上 + 备战席角色、商店角色和本局投资环境给所有攻略打分(已有主 C 5 分、商店里有主 C 3 分、已有最终阵容的其他角色各 1 分、已有前中期角色各 0.6 分、商店里有阵容角色各 0.4 分、投资环境对上 2 分,再加一点热门程度)。

- 开局第一个备战回合把第一名定为当前方向,完整卡片写进本局档案;
- 当前方向的主 C 一个都还没有、别的攻略高出 3 分时,程序自动换;已经有主 C 后只提示「可以考虑转向」,由模型决定;
- 商店刷出了别的攻略的主 C(例如 6 级刷出刃)时单独列出这些攻略;
- 模型用 act 的 `guide` 字段填候选编号改选,改选后程序不再自动换;
- 回合开头给候选(简版卡片),回合中间只有候选变了(刷新商店后)才再给。

`use_guides` 开关还没做。

**2026-11-16 改(第 20.5 节)**:不再每个备战回合重排、自动换攻略和附候选。开局在投资环境页定一篇,之后只在战略检查点比较候选、由模型决定换不换;
备战回合里攻略只体现为「相对当前方向的事实」(商店卡是不是方向里的角色、备战席角色属于前期过渡 / 后期核心 / 无关)。

提供开关 `use_guides: true|false`,关闭后不给指引卡,用于对比模型不靠攻略时的水平。

**效果标签**:投资策略、投资环境、主角光环、奇遇伙伴按描述关键词自动打上效果标签(节点结构 / 商店概率 / 经济 / 人口 / 装备 / 升星),用于:标出会改变流程的修正、在选择类决策中提醒模型评估流程影响、触发重规划。关键词规则在 `knowledge/build.py`,标签只是提示,不代替描述原文。

## 6. 感知层

2026-11-16 起决策模型直接看截图,本节描述的 OCR / 模板感知改为辅助:负责界面分类与规则处理、读数字、名字链接知识库、
算局面要点、给截图标号和点击坐标。截图怎么交给模型、标号怎么画见第 20.3 节。

### 6.1 截图

- 按窗口标题「崩坏:星穹铁道」和窗口类 `UnityWndClass` 定位游戏窗口,取客户区(不含标题栏)截图;进程需声明 DPI 感知,否则坐标会偏。
- 截图用 `PrintWindow`(`PW_CLIENTONLY | PW_RENDERFULLCONTENT`,参考 M7A 的后台截图):让窗口自己把客户区画到内存位图,游戏被其他窗口挡住、上面叠着系统通知或桌面挂件时也能截到干净的画面,窗口不能最小化。2026-11-14 实测 1920x1080 每次约 20ms,和原来的 `mss` 一样快;游戏被遮挡时 `mss` 截到了挡在上面的窗口,`PrintWindow` 没有。`PrintWindow` 失败或在前台时截到全黑,才退回 `mss` 截屏幕上的这块区域;不在前台时不退回(会截到遮挡物),直接报错。
- 所有区域坐标以 1920x1080 为基准做归一化,集中存放在 `config/regions.yaml`,运行时按实际客户区尺寸换算。
- 感知层的所有函数只接收图像(numpy 数组),不直接碰窗口,这样在非 Windows 平台上也能对 fixtures 完整测试。

### 6.2 画面分类

每帧先判当前界面:`home` / `mode_select` / `difficulty` / `environment_choice` / `companion_reveal` / `node_select`(若有节点选择或地图) / `prepare` / `battle` / `augment_choice` / `supply` / `spotlight_choice` / `tea_break`(幕后茶歇) / `commission`(委托) / `special_shop`(羁绊专属商店等) / `event_choice`(其他带选项的事件) / `settlement` / `popup_*` / `unknown`。带括号的几类界面的样子和交互方式待游戏内确认;列表会随采集到的界面增加。

M7A v2026.11.18 的新增页已接入分类:`clara_mod`(机心巧匠改装,战略层)、`mentor`(从师,战略层)、
`equipment_reward`(选择装备,选择层)。从师光环后的备战画面先等待后续页,等待约 18 秒仍未出现时交回模型核对。
配对投资策略按左 1 张 / 右 2 张分组选择和刷新,右组的两张策略一起记入已选事实;布局和机制仍待实机核对。

开局入口先判断当前位置。已在货币战争首页、模式页或难度页时沿当前页继续;已在对局时不运行入口导航。
其他页面参考 M7A 页面图按「大世界→手机→指南旷宇纷争→货币战争→前往参与」导航,每次只执行一步并重新识别。
指南右侧详情确认是货币战争后才点前往参与;未知菜单最多按 Esc 恢复 3 次,操作未推进时暂停并保留现场。

启动前清理旧局时,结算按页面重新识别:评价页「下一步」→阵容总结「下一页」→伤害统计「返回货币战争」→首页。
总结页的「本局奇遇」是栏目标题,不当作伙伴横幅。按钮漏读时用已实测的底部中心位置,
每页连续尝试 4 次未推进即暂停;同属结算的不同页分别计数。

每个界面 1–3 个锚点:固定 UI 元素的模板匹配 + 关键区域 OCR 关键词。界面定义集中在一个注册表里(界面名、锚点、对应的提取器、是否需要决策),新增界面只加一条。

### 6.3 状态提取

| 信息 | 手段 |
|---|---|
| 金币、生命、等级、经验、阶段号、连胜 | 区域 OCR(RapidOCR);整屏识别漏读时单独截那一块放大再认(M7A 的经验:91 会漏成 9,上场人数左边的小人图标会被认成 1)。商店展开时生命和上场人数被商店挡住,用商店收起时读到的(上场人数在上下场、出售后由程序跟着改) |
| 商店角色名与费用 | 区域 OCR + 角色名全集最近邻纠错(编辑距离);名字和价格合成一段时按 M7A 的写法拆开;价格是费用 3 倍的是二星卡 |
| 前台 / 后台 / 备战席的角色 | 头像模板匹配(M7A 头像 → 官方图标 → 商店学到的立绘,见 6.4) |
| 星级 | 卡片底部星星的颜色计数;蓝星表示选了主角光环(维护者告知),也是 1~3 星 |
| 卡面费用 | 卡片最下方色条的颜色(灰、绿、蓝、紫、金 = 1~5 费,M7A 的调色板;只认最下面那段左右均匀的色条,立绘里的近似色不算) |
| 备战席的特殊格 | M7A 的模板:乱流格(站在里面的角色下个节点被换成同费用的别的角色)、「N 节点后解锁上阵」的锁 |
| 背包里的装备 | 官方装备 icon 模板匹配 |
| 角色身上的装备 | 不从画面读:程序装备时记进本局档案(维护者:装备是可追溯的) |
| 三选一、主角光环、投资环境、奇遇的选项文字 | 弹窗区域 OCR + 对应名字全集纠错 |
| 当前节点类型、位面 | 区域 OCR / 图标模板 |
| 委托等局内目标的要求、进度、奖励 | 区域 OCR |
| 界面上显示的规则修正状态(如「轮岗」本阶段翻倍的费用,若游戏有显示) | 区域 OCR(待确认游戏是否显示) |
| 通用事件界面的全部文字和选项 | 全屏 OCR,按位置分组成「标题 / 说明 / 选项」 |

每个字段带置信度;低于阈值时重新截图再提取一次,仍低则在 GameState 中标记该字段不确定,由决策层保守处理。

### 6.4 模板库

`role_list[].icon` / `big_icon`、`equipment_list[].icon` 等是 CDN 图片地址。知识同步时全部下载,统一缩放,生成 `data/templates/roles/`、`data/templates/equipment/`。游戏内显示的头像可能有裁切、边框、星级角标,匹配前需要按 fixtures 调整裁切区域和匹配方法(这一步只能在拿到 fixtures 后做)。

棋盘卡面的角色识别(`vision/board.py`,2026-11-14 实测):

- **卡面跟着皮肤换**:装了皮肤的角色(例如火花「甜梦电波」)卡面和官方图标不是同一张图,只靠官方图标认不出。
- **M7A 头像为主**:March7thAssistant 仓库的 `assets/images/share/character/`(约 100 张,含皮肤)和名字表 `assets/config/character_names.json`,知识同步时下载到 `data/templates/avatars/`。和卡面是同一套立绘、比例接近。名字表里的皮肤(「火花·甜梦电波」「流萤「春日手信」」)和各命途的开拓者、三月七归到本体;「砂金·戏浪」这类在货币战争里是单独角色的,按全名优先对上。
- **比对方法**(参考 M7A 的头像比对:只比中央、避开角标、多倍率):头像中央取 64x64 像素,按卡宽缩放(宽 113 像素的卡面上 0.9 倍),只在卡面中央附近的窗口里找;先用一个倍率比所有头像,再对前几名细调倍率。认对的 ≥0.8,认错的 ≤0.73,门槛 0.75。在 96 张备战截图上,原图的角色卡从 377/426 认出提高到 422/426(剩下 4 格是搜索框遮挡),没有认错;一帧约 0.2 秒。
- **兜底**:M7A 没有的角色(帕姆王)和以后的新角色、新皮肤,用官方图标和商店卡片学到的立绘(门槛 0.6)。M7A 2026-11-15 版补上了星神★阿哈的两张头像。
- **还认不出就点开看**(M7A 的做法:M7A 本身不比头像,而是逐张点开读详情面板里的名字):备战回合开始、商店收起时,认不出的卡逐张点开,读右侧详情面板「前台 / 后台 / 前后台」标签正上方的名字,点左上角最边上的空白关掉;把卡面中央(和 M7A 头像中央 64 像素对应的那块)存到 `data/templates/learned/`,之后和 M7A 头像一起比。每个节点最多点 3 张。在 31 个实机详情面板上名字都读对或读不出(「白露」被拆成「露」时对不上任何角色,不会学错)。
- **开拓者的名字**:开拓者在商店、补给、角色详情里显示的是玩家自己取的名字(M7A 也要用户配置:`currencywars_remembrance_trailblazer_name`)。配置 `agent.trailblazer_name` 后,文字识别结果里的这个名字统一换成「开拓者」。

### 6.5 标定与采集工具

- `cwagent collect`:在 Windows 上运行,用户手动打游戏时按热键或定时截图,保存客户区原图到 `data/fixtures/<日期>/`。
- `cwagent regions check <截图>`:把 `regions.yaml` 中所有区域框和名字画到截图上输出一张图,用于肉眼校对坐标。
- fixtures 按界面归档后,每个提取器都有对应的单测;每张 fixture 配一个人工确认过的期望 GameState(JSON)。

### 6.6 验收

fixtures 上:画面分类 100% 正确;字段提取 ≥ 95% 正确。

## 7. GameState

## 8. 决策引擎

### 8.1 分层

| 层 | 触发 | 输入 | 输出 |
|---|---|---|---|
| 反射层(规则) | 每帧 | 界面类型 | 确定性动作(点继续、跳过、领奖、关弹窗);或"需要决策" |
| 选择类(LLM) | 出现三选一类界面 | GameState + 候选项官方描述 + 对局方向 | `choose(idx)` 或刷新 |
| 通用事件(LLM) | 幕后茶歇、委托等专属交互,以及没有专门处理器的带选项界面 | 画面全部文字与选项 + GameState + 对局方向 | `choose(idx)`、`skip` 或 `pause`(看不懂时请求人工) |
| 战略层(LLM) | 投资环境和奇遇伙伴都确定后 1 次;触发式重规划 | 开局信息(含全部规则修正) + 前几张指引卡 | `RunDirection` |
| 战术层(LLM) | 每个备战阶段 1–3 次 | GameState + RunDirection + 实体描述 + 羁绊状态 + 最近动作记录 + 经验 | 有序动作列表 |

**2026-11-16 改(第 20.5 节)**:战略层落实为固定的「战略检查点」(选投资环境、每个位面读完词条和节点后、首领前、连输两场或血量跌破阈值、
拿到会改变流程的修正后),模型在检查点更新自己的笔记;攻略候选只在检查点给,新的相关经验只在检查点检索
(这局想起过的经验每个回合开场按当前局面重新判断还适不适用,2026-11-18)。备战回合只执行方向。

战术、战略、选择、复盘各自可在配置里指定模型档案;默认全部用同一个。另有**导航层**(`roles.navigator`):没见过的界面、难度选择等只是找路的界面,可以配便宜、不思考的档案(例如 DeepSeek 的 `thinking: {type: disabled}`)。网页上开局时选的模型用于战术、战略、选择三层(便于对比模型),导航层配置了就用配置的。思考强度是档案的 `reasoning_effort`(none / low / medium / high / xhigh / max,界面上直接显示这些英文档位;none 是关闭思考,不填用厂商默认),网页开局时可以给这一局另选,覆盖战术、战略、选择三层,导航层不变(2026-11-17 维护者要求);其他厂商差异写在档案的 `extra_body` 里,代码不判断。

### 8.2 对局方向(RunDirection)

模型自己写的方向,不是脚本。字段都是自由文本或名字列表,不设必须达成的检查点。

```yaml
archetype: "连击 + 奇兽花园"
reference_guides: ["<指引卡 id>"]        # 参考了哪些卡,可为空
carry_candidates: [阿格莱雅, 那刻夏]
plan: >
  前期用那刻夏和低费连击角色保连胜;6 级前不主动 D 牌;拿到阿格莱雅后把输出装转给她……
economy_notes: "…"
pivot_conditions: "到位面2中段仍没有任何主C 2星,或出现更契合当前环境的核心角色时考虑转型"
```

重规划触发:战术层在输出里设置 `request_replan: true` 并给出理由;或规则触发(生命低于阈值、连续多个阶段主 C 未成型、新拿到带「节点结构 / 商店概率 / 人口」标签的规则修正、出现新的委托)。重规划的输入包含旧方向和当前局面。

### 8.3 战术层的动作空间

**实现情况(2026-11-14)**:工具名为 `act`,已实现 `buy`、`sell`、`move`、`refresh`、`buy_exp`、`ready`(`orchestrator/prepare.py`),格子编号对模型从 1 开始;装备、晶矿等暂时仍用坐标类操作(click / drag)。程序在备战回合开始时先打开商店,让模型第一眼看到商店。商店是否展开看右下「收起」/「商店」、右侧「刷新」和中间一行抽卡概率(角色详情会遮住右下按钮);开关商店后等卡片名字连续两次读到一样再继续,动画期间读会读错。进入备战时屏幕中央的「备战阶段」横幅动画期间点击无效,先等。`roll_until`、`level_to`、`equip`、`lock_shop` 还没做。2026-11-16 定的新增操作(`roll_until`、`level_to`、按目标装备合成、`use_item`、
`inspect`、`zoom`、按标号 `click`)见第 20.6 节。下面是原设计:

一次调用通过一个工具 `submit_actions` 提交:

```json
{
  "analysis": "对当前局面的判断(给人看的,会显示在观战页)",
  "actions": [
    {"op": "buy", "args": {"slot": 0}, "reason": "那刻夏凑2星"},
    {"op": "move", "args": {"from": {"zone": "bench", "idx": 0}, "to": {"zone": "back", "idx": 1}}, "reason": "…"},
    {"op": "roll_until", "args": {"targets": ["阿格莱雅"], "gold_floor": 30, "max_rolls": 5}, "reason": "…"},
    {"op": "ready", "args": {}, "reason": "…"}
  ],
  "request_replan": false,
  "notes": [{"kind": "教训", "title": "…", "content": "…", "entities": ["经济严重过热"], "nodes": ["reward"]}]
}
```

| op | 参数 | 说明 |
|---|---|---|
| `buy` | `slot` | 买商店第几格 |
| `sell` | `zone`, `idx` | 卖掉某格的角色 |
| `refresh` | — | 刷新商店;**其后的动作全部作废**,重新感知后再调用模型 |
| `buy_exp` | `times` | 买经验 |
| `move` | `from`, `to` | 在前台 / 后台 / 备战席之间移动或交换 |
| `equip` | `item`, `zone`, `idx` | 把背包里的装备给某角色 |
| `craft` | `item_a`, `item_b` | 合成(如果游戏里合成是通过把两件装备给同一角色自动完成,则此动作在执行层映射为对应操作;以实际界面为准) |
| `lock_shop` | `locked` | 锁定 / 解锁商店 |
| `roll_until`(宏) | `targets[]`, `gold_floor`, `max_rolls` | 规则循环:刷新 → 感知 → 商店里有目标就买;金币到下限、次数用完或备战席满即停,把结果交回模型 |
| `level_to`(宏) | `level` | 买经验直到指定等级或金币不足 |
| `ready` | — | 结束备战,开始战斗 |

`notes` 可选,是模型想记下来的规律,写入记忆草稿(5.4)。所有决策工具(选择类、通用事件)都有这个字段。

不使用各厂商的 strict 模式(各家不一致);统一用 pydantic 校验模型输出。

### 8.4 校验器

只拦**客观非法**的动作:金币不够、格子已满、目标格为空、名字不存在、配方不成立、站位类型不允许(后台角色放前台等)、参数缺失。非法时把具体错误信息连同原输出一起重问,最多 2 次;仍失败则执行已通过校验的前缀动作后直接 `ready`。

不设"必须遵循攻略"的约束。只有一条防误操作规则:卖出 2 星及以上角色时 `reason` 不能为空。

每个备战阶段战术调用上限 3 次(`refresh` 和宏返回会消耗次数);超限直接 `ready`。上限放配置里。

**2026-11-16 改**:输入重新分块(系统提示词 / 整局已知事实 / 条目说明 / 本局经历 / 模型笔记 / 当前回合),只在出现新内容时追加,

**2026-11-18 改**:条目说明和想起的经验原来只加不删,没选的投资环境、商店里没买的角色、合成掉的装备、

本局经历挪到最前面。同一份 1-4 局面(模型当时拿到的那一帧,商店收着)用新代码重建,开场从 12156 字降到 7973 字,条目说明从 46 个降到 22 个(第 20.4 节)。

**回合内多轮、回合之间无状态**(2026-11-14 与维护者确认,替代原来的「每个决策点一次无状态调用」):

- **回合**:一个备战阶段,或一个需要选择的界面(投资环境、投资策略、遭遇节点、主角光环、没见过的界面)。回合内是多轮对话:模型调用 `act` 给出一组操作,程序执行后把**执行结果 + 新界面**作为这次工具调用的结果交回,模型接着判断。模型操作后弹出的界面(确认框、角色详情)仍属于原回合。
- **回合结束**:备战阶段点了出战、进入战斗或结算、出现另一个需要决策的界面。对话丢弃,本局经历里留一行:程序记录的做了什么(备战:节点的进场数字、操作、阵容)+ 模型在结束回合的 act 里写的回合小结(`summary`,≤150 字;没写就用它最后的判断开头)。战斗结果、本局学到的教训(`notes`)也各记一行。
- **轮数上限**:备战回合 `agent.max_tactical_calls_per_stage`(默认 5,不含单独那轮出战;2026-11-16 实机 3 轮在高难下不够,1-1、1-3 都撞上「决策次数用完,直接出战」),最后一轮提示模型以 `ready` 结束,用完直接出战;其他回合 4 轮,超过就开新回合(清掉对话)。
- **本局档案**(`brain/ledger.py`)分两部分。**本局经历**:整局所有回合的记录,只往后追加、写下不改(维护者要求保留之前所有回合,让模型像同一个人在持续操作;一局约 60~90 个回合、两三万字)。**当前状态**:当前参考的攻略、角色身上的装备、没开的道具、本位面节点、模型写的对局方向与计划(`run_notes` 整体改写,≤800 字),随时会变。
- **缓存**:system 整局不变;回合的第一条消息以本局经历开头,后面是整局已知事实、当前相关的条目说明和经验、当前状态。本局经历只往后加,放在最前面**有利于**前缀稳定,能不能命中看厂商:OpenAI 格式靠厂商的自动前缀缓存(不用 `cache_at`),Anthropic 格式在本局经历末尾(`Message.cache_at`)和最后一条消息末尾各打一个缓存标记。回合内只往后追加,前缀一直稳定。缓存命不命中和发的内容过不过期是两回事。
- **思考内容回传**:助手消息原样传回(`Message.raw`)。DeepSeek 思考模式带工具时必须传回 `reasoning_content`,否则 400;Anthropic 要原样传回 thinking 块。
- **回放**:每步记录里保存这一轮发出的新内容(`decision.prompt`),回合的完整对话可以由同一回合的各步拼出来。

以下是原设计中 user 消息的内容清单,现在分布在回合开场消息(本局档案、当前界面、条目描述、相关经验)和后续各轮(执行结果、新界面、新出现的条目)里:

- **system**(稳定,利于缓存):角色设定、规则卡、动作语义与约束、输出要求(先写 `analysis` 再给动作;每个动作必须有 `reason`;用中文)。
- **user**(每次变化),按固定顺序拼:
  1. 本局规则修正:每条的来源、名称、官方描述原文、当前状态(2.3);
  2. 对局方向(RunDirection);
  3. 进行中的局内目标(委托等);
  4. GameState;
  5. 羁绊状态(当前人数 / 已激活档 / 下一档差几人及效果);
  6. 屏幕实体描述(实体链接结果);
  7. 可合成的装备(根据背包和配方算出);
  8. 本备战阶段已执行的动作及结果、上一场战斗的结果;
  9. 相关记忆(5.4),标明类别、置信度和来源;
  10. 本次需要做什么。

选择类决策(投资环境、投资策略、奇遇相关选择)的提示词要求模型逐个评估候选项对流程的影响(节点结构、商店概率、经济),而不只看数值强度。

提示词模板放在 `src/cwagent/brain/prompts/` 下的独立文件里,不要散落在代码中;Trace 里保存每次实际发送的完整提示词。

写提示词时:说明这是一个什么游戏、目标是什么、攻略只是参考;不要堆砌"必须""绝对"这类措辞,不要塞示例动作序列(模型会照抄)。

## 9. 执行层

- 键鼠原语:`click(nx, ny)`、`drag(from, to)`、`press(key)`,坐标为归一化值。输入库先用 `pyautogui`;如果游戏窗口不响应合成事件,依次降级到 `pydirectinput`、Win32 `SendInput`。游戏以管理员权限运行时,agent 进程也必须以管理员权限运行。
- 每个语义动作 = 原语序列 + 前置断言(对应按钮或格子存在)+ 后置校验(金币变化、格子内容变化、商店槽变空)。失败重试 1 次,仍失败则放弃本次动作列表的剩余部分,回到重新感知。
- 已知可用的快捷键(S1 时期,S2 待核实):`D` 刷新商店、`F` 买经验、`Esc` 退出 / 取消。站位移动在 M7A 中用拖拽实现(按下 → 移动 → 抬起)。
- 动作之间加入小的随机延迟。
- 截图等待(2026-11-17 改,参考 trail-cli「截图为准,冲突时补读」):界面观察及备战动作的后置核对共用 `settle`,
  每 0.3 秒比一次整屏平均差,低于阈值就识别,最多比 6 次(约 2 秒),停止信号在等待期间仍会检查。
  之前为了等升星动画改成「九宫格里变化最大的一块连续 3 次稳定、最多 18 秒」,结果乱流格这类一直在闪的局部光效
  (位置每个节点随机)让每次截图都等满 18 秒,备战的固定流程也因超时被跳过(2026-11-17 实机,备战席那一块每次变化 3.5~5.7)。
  局部动画造成的误读改由两处兜底:读星级时用 settle 留下的前一帧再读一遍,两帧不一样就报「星级待定」(`board.confirm_stars`);
  模型发现截图和程序识别对不上时单独提交 `recheck`,程序等 1 秒后重新截图识别,列出和上一轮相比变了的格子,不占决策次数。
- **出战人数没满时拦下**(2026-11-16,参考 trail-cli):点出战后弹出「可出战角色人数未达上限,是否确认出战?」时点「取消」,
  把「上场 x/y」作为执行结果交回模型;不勾「本局不再提示」。原来是勾上后确认,之后少上人游戏也不再提醒(最近 6 局每局都发生)。
- **拿不准的缓存标成过期**(2026-11-16):程序记住的上场人数、等级等,在可能变化的操作(买经验、上下场、出售)之后要么重读、要么标成过期;
  过期的值不用来拦模型的操作,改成操作后核对。原来买经验升级后上场上限没更新,模型的上场被程序自己拦下。
- **开晶矿**(2026-11-14 实机验证):用虚拟 Xbox 手柄(ViGEmBus + vgamepad)。推一下摇杆,游戏切到手柄界面,晶矿上显示「开启 LT + RT」;同时按 LT、RT 一次打开全部晶矿(实测 4 个一次全开);再动一下鼠标热切换回键鼠界面(维护者告知的做法)。用摇杆而不是按键触发切换,避免误触。切到手柄界面时商店有时会自己展开、挡住「开启」提示(2026-11-14 实机两次),这时按 B 收起。手柄用不了或还是没看到「开启」时改用鼠标:按 M7A S2 版 `_gather` 的做法,对每个检测到的晶矿以它当前位置为中心横向划过(左右各约 87 像素,0.5 秒;晶矿会漂移,每次重新定位),连续两次个数没减少就停(待实测:原来在固定位置横向划动两次都没效果)。
- **有没有晶矿**(2026-11-15 改,参考 M7A S2 版的 `reward_orbs`):在面板里(1275~1624, 202~465,避开上方道具栏)用霍夫圆找晶矿球,按圆心颜色(蓝、灰白、金)筛掉浮窗文字等误检,去掉重叠的重复圆;奇遇的倒计时礼盒(在面板上停留好几个回合,模板取自 M7A)范围内的圆不算。商店展开时卡片会被认成很多圆,只在商店收起时检测。刚掉落、还在放特效时个数会跳,开之前等个数稳定。用第一、二位面 21 张实机截图核对:空面板(含「金币说明」浮窗遮挡)全是 0,有晶矿时都检出,单独摆放时个数准确。原来的「和空面板比对」会把礼盒、浮窗、新位面背景都当成有晶矿,开了没变化就记失败,已不用。
- **开晶矿的时机**(参考 M7A):每个备战回合一开始、买东西之前先开(先收起商店、等弹窗过去);模型点出战前再看一次(回合中途拿到的、开头因为备战席满了没开成的),开到东西就先不出战,让模型看看新局面,每个节点只拦一次。没开成只放过当前节点(同一节点连续 2 次),下个节点照常再开。原来累计 3 次(连成功也算进去)就整局不开,2026-11-14 那局 1-8 失败一次后,1-9、2-1、2-4 面板里攒了 8~13 个晶矿都没开。晶矿里的角色需要空的备战席(M7A:「晶矿需要空备战位」),备战席满时界面中间提示「备战席已满」,不算失败,提示模型出售或上场角色腾位置,出战前再开。
- 安全措施:
  - 只在分类器识别为货币战争相关界面时才执行动作;识别到其他界面(抽卡、商城、充值等)立即停止并报警;
  - `--approve` 开关:每个动作列表执行前在终端或观战页等待人工确认(首次联调用);
  - 停止:停止快捷键(Ctrl+Alt+F10,被占用时依次换 Ctrl+Alt+F9、Ctrl+Shift+F10)或观战页点停止,在下一个键鼠操作前生效;鼠标甩到屏幕角落急停。不根据鼠标移动、键盘活动判断有人在用电脑:游戏会自己挪光标(节点切换时居中),太容易误判(维护者要求,2026-11-14);
  - 单局步数上限和时长上限(默认 120 分钟)。

## 10. 编排与可靠性

### 10.1 主循环

流程完全由画面驱动(2.3 原则 1):每一步截图、判断界面,再决定做什么;不维护「现在应该到第几个节点」这类假设。

- **等画面稳定再识别**(2026-11-14):每隔 0.3 秒截一张、缩成 96x54 灰度比较,平均差小于 3 才 OCR 和分类,最多等 6 次;战斗中不等。没有有效文字(只有 UID、延迟数字)的画面当作过场直接等,不调用模型。
- **规则处理的界面**:点击继续、点击空白加速、开局介绍、主页、模式选择、节点结算(「继续挑战」)、出战确认(勾「本局不再提示」后确认)、上一局的结算(翻页 / 返回)、误按 Esc 弹出的中断确认(再按 Esc,3 次关不掉就暂停)、战斗中(交给战斗监视,见下)、整局结算。参考 M7A S2 版补上的(2026-11-15):断线重连提示(确认按钮点亮才点)、云游戏连接中断(暂停)、「点击空白处关闭」、助燃券到上限、「前台区域无角色」、主角光环与奇遇详情(只是查看,点右上角 X 关掉;模型以前关它时点错过好几次)、开拓商店里星穹列车价格为 0 时免费启动、在开拓商店停留超过 6 步直接关掉。
- **战斗监视**(`orchestrator/battle_watch.py`,维护者要求,2026-11-15):进入战斗后不再每 4 秒截图、整屏识别(大招立绘和特效会挡住行动值,画面被认成别的界面时还会叫醒模型),而是一直看到战斗结束:每 0.25 秒按颜色找画面中间偏上的红色横幅,找到再识别那一条文字——「受到致命攻击,战斗倒计时减少!」是阵亡(只停留约 1 秒),其他文字是敌方机制提示;每秒读一次行动值、每 2 秒读一次进度;行动值条目连续 2.5 秒看不到或每 8 秒一次的整屏识别认出已经不是战斗,就结束。记录里只留进入战斗时的一张截图,结束后在本局经历里写一行(行动值、进度、阵亡次数和前后的行动值、敌方提示、用时)。在旧对局截图里颜色命中的 14 处,12 处是敌方提示横幅、2 处是红色特效,文字都分得开;阵亡横幅 2026-11-16 第一次在实机认出(那局 1-7,颜色和行数都在阈值内),漏检率未知。阵亡只认横幅:原来把行动值单次下降 ≥35 也按阵亡算,核对两局实机记录,这样的下降十几处全是误读(「104 → 6 → 90」)或大招挡住几十秒没读到,唯一认出横幅的那场一次行动值都没读到;现在给模型的只有进度和行动值的首尾读数(各取三次中位数)、认出的横幅次数,认出横幅时另存一张整屏图供核对。报表的「阵亡横幅」列同此;没截到结算界面的战斗按下一个节点进场血量补胜负(标「按血量」)。
- **打开商店后重新判断界面**:程序在备战回合开头打开商店时,游戏可能正好弹出投资策略、补给等界面;这时交给下一步按新界面处理,不再按备战界面问模型。
- **备战的执行与核对**(2026-11-15 第一局外部 agent 实测后,维护者要求):
  - 出战单独一轮:模型把买卖、上场和 ready 一起发时,程序先执行别的操作、不出战,把操作后的实际局面交给模型,确认无误再单独发 ready。备战回合因此多给一轮;最后一轮例外,前面的操作都成功才接着出战。起因:上场被游戏拒绝(「当前情况下不可调整」)时程序照样报成功,模型按想象中的阵容出战。
  - 上场、换位后看一眼:界面中间出现拒绝提示,或目标格还是空的,就按最新的商店开合状态换算坐标重试一次,还不行就停下,后面的操作不做。
  - 合成后装备栏会重新排序(实测:1 号和平手枪 + 2 号折叠小刀合成后,原来 3 号的生命之花排到了 1 号,模型按「成品在小编号那格」把生命之花当武器大师装了出去):合成后报告读到的新装备栏,同一轮里后面的合成 / 装备不做,让模型按新编号再发。装备后按名字核对装备栏少掉的是不是那一件。
  - 每一轮都由程序打开右下角的角色商店。棋盘左上角写着「打开商店」「有商品可购买」的是羁绊专属商店(开拓银轨的开拓商店等)的入口,一直挂着:以前被当成弹窗,每个备战回合都等满 8 秒后跳过了开晶矿、收集位面节点;模型也把它当成角色商店去点。现在不算弹窗,并在提示里说明它是什么。
- **投资界面**:刚进投资环境选择时有约 3 秒的特效(维护者告知),先等过去再识别;投资环境和投资策略的三张卡是依次翻出来的,等三张卡的标题都认出来(最多再等 4 秒)再交给模型(实测:第三张没翻完时只认出半句效果说明)。
- **敌人词条**(维护者要求):位面详情底部那一排(如「前台熄火」「开局不利」)会左右全局方向(「虚数熄火」就不用虚数主 C,「能量逃逸」就不用靠能量放大招的主 C)。官方接口没有词条数据,收集位面节点时逐个点开读说明,存进本机词条库 `data/affixes.local.yaml`(已知的不再点),写进本局经历;第一次收集在 1-1,所以开局方向在 1-1 还能按词条调整。点开后的说明面板布局还没实测,每张说明截图存到对局的 `debug/`。
- **战斗数据在网页上**:对局页战斗那一步画出剩余行动值和进度两条曲线(共用时间轴,不共用纵轴),标出阵亡时刻,列出阵亡和敌方机制提示。
- 2026-11-14 用两局记录离线估算:原来 92 次模型调用的那局,新逻辑下需要模型的回合约 27 个;另一局 24 次 → 约 5 个回合。

```
Detect(截图 + 分类)
  ├ 已知界面、无需决策 → Reflex → Execute → Detect
  ├ 已知界面、需要决策 → Decide → Validate → Execute → Detect
  ├ 战斗中 → 战斗监视(不存截图、不调模型,直到战斗结束)
  └ 未知 / 卡死 → Recover → Detect
```

- **卡死判定**:阶段号连续多次未变化且界面无进展,或连续多次未知界面。
- **恢复流程**:`Esc` 逐级退出 → 重新进入 → 必要时「放弃并结算」。恢复时保存截图到 `runs/<id>/debug/`。
- **对局控制**:开始、暂停(在下一个决策点前停住)、继续、停止;可从命令行或观战页触发。
- **未结算的旧对局**:进入时若发现有未结算对局(M7A 中的识别文字是「结束并结算」/「放弃并结算」),按配置选择继续或放弃。

### 10.2 界面处理器与通用事件

- 每类界面在注册表里登记一个处理器(界面名、锚点、提取器、处理方式:反射 / 选择类 / 战术 / 通用事件)。奇遇伙伴、羁绊带来的专属界面(幕后茶歇、委托、专属商店等)各自登记,随采集到的界面逐个补充。
- **盖在备战界面上的面板**(M7A S2 版的界面清单,2026-11-15 补):开拓商店、黑市商店、巡海游侠任命、梦境交织共舞、奇兽花园、骇入效果、替换已有光环。背景里仍有「备战阶段」,要先于备战界面判断(开拓商店曾被当成备战界面,点商店只提示「该状态下不可使用」,卡住一个节点后暂停);交给三选一层的模型,附上布局和关法。选项界面里「确认」还是灰的时提示模型先选够(补给「已选择0/1」时灰、「1/1」时亮,实测)。
- **通用事件处理**:界面能判断为「带选项的事件」但没有专门处理器时,全屏 OCR 得到标题、说明和选项,交给模型选择;模型也可以回答 `pause`,表示看不懂,此时暂停对局并在观战页报警。
- **完全无法识别的界面**:先按 10.1 的恢复流程尝试;仍无法识别则暂停,保存截图到 `runs/<id>/unknown/`,用于之后补处理器。不在看不懂的界面上乱点。

## 11. LLM 接入层

### 11.1 原则

- 不安装 `anthropic`、`openai` 等厂商 SDK,用 `httpx` 直接发请求;
- 不锁定厂商和模型:厂商只描述"接口格式 + 地址 + key",可用模型从厂商接口拉取后由用户选择;
- 代码里不出现任何具体厂商名、模型名或按模型名分支的逻辑,换模型只改配置。

### 11.2 厂商与模型档案

配置分两层:

- **厂商(provider)**:接口格式 + 地址 + key,同一个 key 只填一次;
- **模型档案(model)**:选一个厂商 + 一个模型 id,再加该模型自己的思考强度和透传参数。同一厂商可以建多个档案,用来对比不同模型或同一模型的不同参数。

```yaml
providers:
  - name: my-provider               # 厂商名,自己起
    format: openai                  # openai | anthropic
    base_url: https://api.example.com/v1
    api_key: sk-…
    extra_headers: {}               # 原样合并进请求头
    anthropic_version: "2026-10-21" # 仅 anthropic 格式使用;部分网关只认 2023-06-01

models:
  - name: my-model                  # 档案名,界面上显示和选择用
    provider: my-provider
    model: some-model-id            # 从厂商的模型列表里选,或手动填写
    max_tokens: 16000               # anthropic 格式默认 16000;openai 格式不填则不发送
    reasoning_effort: high          # 思考强度:none / low / medium / high / xhigh / max;不填则不发送,用厂商默认
    extra_body:                     # 原样合并进请求体:思考开关等厂商参数
      thinking: {type: enabled}
    extra_headers: {}               # 与厂商的 extra_headers 合并
    tool_mode: native               # native | json
    timeout_seconds: 300

roles:                              # 各决策层用哪个模型档案;留空则用第一个
  tactical: my-model
```

调用时把厂商和模型档案合并成一个完整的调用参数(`ModelEndpoint`),LLM 接入层只认这个。

**思考强度**(2026-11-17):各家写法已经比较统一(2026-11-17 查 DeepSeek、Claude 文档):OpenAI 格式发 `reasoning_effort`,
Anthropic 格式发 `output_config.effort`,`none` 在 Anthropic 格式下发 `thinking: {type: disabled}`。档位由厂商解释:
DeepSeek 只有 low / high / max(medium、xhigh 当 high),OpenAI 没有 max,Claude 新模型思考一直开着、不能关,不支持的档位用「测试连接」能看出来。
DeepSeek 的 `thinking` 开关优先于 `reasoning_effort`,所以 `extra_body` 里写了开关时按思考强度改(none 改成关,其他档位去掉「关」);
思考强度盖过 `extra_body` 里写死的同名参数。旧档案写在 `extra_body` 里的 `reasoning_effort`、`output_config.effort`、`thinking: disabled`
读配置时搬到 `reasoning_effort`。

**模型列表**:openai 格式 `GET {base_url}/models`,anthropic 格式 `GET {base_url}/v1/models`(按 `has_more` / `last_id` 翻页)。部分兼容网关不提供这个接口(例如 2026-11 时 DeepSeek 的 Anthropic 兼容接口返回 404),此时提示用户手动填写模型 id。

`config.yaml` 含 key,必须在 `.gitignore` 中;仓库里放 `config.example.yaml`(不偏向任何厂商)。后端接口返回厂商时 key 只显示掩码(前 4 位 + 后 4 位);修改厂商时提交空 key 或掩码表示沿用原 key。

### 11.3 统一接口

```python
class LLMResponse(BaseModel):
    text: str                 # 可见文本
    reasoning: str            # 思考内容(没有则为空)
    tool_calls: list[ToolCall]   # name + arguments(dict)
    usage: Usage              # input_tokens, output_tokens, cache_read_tokens, cache_write_tokens
    stop_reason: str
    latency_s: float
    raw: dict                 # 原始响应,进 Trace

def complete(profile, system: str, user: str, tools: list[ToolSpec]) -> LLMResponse
```

`ToolSpec` = `name` + `description` + `parameters`(JSON Schema)。两个适配器各自只做请求体构造和响应解析,放在 `llm/openai_format.py` 和 `llm/anthropic_format.py`。

**流式**(2026-11-18,维护者要求网页上实时看到模型在想什么):`complete(..., on_delta=回调)` 时发流式请求。
OpenAI 格式加 `stream: true` 和 `stream_options: {include_usage: true}`(最后一块带用量,choices 为空);
Anthropic 格式加 `stream: true`,`thinking_delta` / `signature_delta` / `input_json_delta` 按块拼回。两边的 `Accumulator`
把流里的事件拼回成和非流式**完全一样**的响应再交给原来的 `parse_response`,所以思考的回传(DeepSeek 的
`reasoning_content`、Claude thinking 块和签名)、工具参数解析、用量都不变;边收边回调 `reasoning` / `text` / `tool`
(工具参数片段)三种增量,重试或重问前回调 `reset`。流里的 error 事件(过载)按可重试处理。网关不认流式参数
(400 / 422)时马上改用非流式重发,非流式成功才记下这个接口本进程里以后不再试流式(400 也可能是别的原因)。
外部 agent 不流式。

**图片输入**(2026-11-16,第 20.3 节):`Message` 可以带图片(JPEG 字节)。OpenAI 格式放在 user 消息的 `image_url`(data URL)里;
**tool 消息只能放文字**(OpenAI 文档:「For tool messages, only type `text` is supported」,2026-11-16 查),所以工具调用之后的截图
放在紧跟的一条 user 消息里。Anthropic 格式放 `image` 块(user 消息,以及 `tool_result` 的内容里,实现时以官方文档为准)。
JSON 模式与 OpenAI 格式相同。连通性测试改成发一张写着随机数字的小图,看模型能不能读对。

### 11.4 OpenAI 格式

- `POST {base_url}/chat/completions`(`base_url` 自带 `/v1`),头:`Authorization: Bearer <key>`、`Content-Type: application/json`。
- 请求体:

```json
{"model": "…",
 "messages": [{"role": "system", "content": "…"}, {"role": "user", "content": "…"}],
 "tools": [{"type": "function", "function": {"name": "…", "description": "…", "parameters": {…}}}],
 "tool_choice": "auto"}
```

- 响应解析:`choices[0].message.content` → text;`choices[0].message.tool_calls[].function.{name, arguments}`(`arguments` 是 JSON 字符串,需解析)→ tool_calls;思考依次尝试 `message.reasoning_content`、`message.reasoning`,再尝试回复开头的 `<think>…</think>`;`usage.prompt_tokens` / `completion_tokens` → usage,缓存命中取 `prompt_tokens_details.cached_tokens` 或 `prompt_cache_hit_tokens`,思考 token 取 `completion_tokens_details.reasoning_tokens`;`choices[0].finish_reason` → stop_reason。
- 2026-11-14 用 DeepSeek(`deepseek-flash`,两种格式)实测通过:工具调用、思考内容(`reasoning_content`)、缓存命中均能正确解析。请求很简单时模型可能不输出思考内容。

### 11.5 Anthropic 格式

- `POST {base_url}/v1/messages`,头:`x-api-key: <key>`、`anthropic-version: 2026-10-21`、`Content-Type: application/json`。版本号做成档案可覆盖的字段(第三方网关可能只认旧版本号 `2023-06-01`)。
- 请求体:

```json
{"model": "…", "max_tokens": 16000,
 "system": [{"type": "text", "text": "…", "cache_control": {"type": "ephemeral"}}],
 "messages": [{"role": "user", "content": "…"}],
 "tools": [{"name": "…", "description": "…", "input_schema": {…}}]}
```

- 响应解析:遍历 `content[]`,`type=="text"` → text,`type=="thinking"` → reasoning(取 `thinking` 字段),`type=="tool_use"` → tool_calls(`name`、`input` 已是对象);`usage.input_tokens` / `output_tokens` / `cache_read_input_tokens` / `cache_creation_input_tokens` → usage;`stop_reason` 原样保留。
- 注意事项(截至 2026-11 的 Claude API 行为,写进适配器注释和 `config.example.yaml`):
  - 不要发送 `temperature` / `top_p` / `top_k`,新版 API 会拒绝;
  - 新一代 Claude 模型不接受强制工具调用(`tool_choice` 为 `any` 或指定工具会 400),所以始终用默认的 auto,靠提示词要求调用工具;没有返回工具调用时按 11.6 重问;
  - 思考内容默认不返回,需要在档案的 `extra_body` 里写 `thinking: {type: adaptive, display: summarized}` 才能拿到摘要;较老的模型用 `thinking: {type: enabled, budget_tokens: N}`。这些都由档案决定,代码不判断;
  - `stop_reason == "refusal"` 时当作一次失败调用处理并记入 Trace;不启用服务端自动回退到其他模型的功能,因为那会让别的模型代答,破坏模型对比。

### 11.6 工具调用的统一与兜底

- `tool_mode: native`:走各格式的原生工具调用。响应里没有工具调用时,带一句提示重问 1 次。
- `tool_mode: json`:不传 `tools`,在 user 末尾附上工具的 JSON Schema 和"只输出一个 JSON 对象"的要求,从回复文本中提取 JSON(取最后一个完整的 JSON 对象或 ```json 代码块)。给不支持工具调用的模型和网关用。
- 两种模式的结果都经过同一个 pydantic 校验。

### 11.7 重试与错误

- 429、5xx、网络错误:指数退避重试(默认最多 4 次),有 `retry-after` 头时遵循;
- 其他 4xx:不重试,抛出带状态码和响应体的错误,记入 Trace,前端显示;
- 连续 3 个决策点调用失败则暂停对局并报警。

### 11.8 连通性测试

设置页的"测试"按钮(命令行 `cwagent models test`)用该档案发一个最小请求(一句话 + 一个简单工具),返回是否成功、是否拿到工具调用、是否拿到思考内容、耗时和 token 用量。


### 11.9 外部 agent 接入(MCP)

2026-11-14 与用户确认方向,先适配 DSH(DeepSeek Harness,开源、可定制);2026-11-16 加上 Claude Code(插件);Codex 的接法未实测。

**目的**:让用户用自己的 agent 工具下棋,用的是这些工具自己的模型和额度(订阅、账号)。由用户自己打开 agent 工具并连上本服务;本服务不启动它们、不读取或转发它们的登录凭据。

**为什么不由本服务去调用 `claude -p` / `codex exec`**:Anthropic 条款不允许第三方产品代用户使用订阅凭据;每次调用都要启动一次 CLI,Codex 每次还固定多约 12k token(2026-11-14 在 Mac 上实测);MCP 是通用协议,任何支持 MCP 的 agent 都能接,代码里不出现厂商名。参考过的同类做法:Netcatty、Open Design 都是调用用户本机的 CLI,自己的能力通过 MCP 交给 agent。

**形态**:

- `cwagent serve` 在 `/mcp` 提供 MCP 服务(Streamable HTTP)。不用 stdio:serve 跑在用户桌面会话里、握着游戏窗口,stdio 服务由 agent 工具当子进程启动,在 SSH 会话里启动时截图是黑的;HTTP 也让 agent 可以跑在另一台电脑上。
- 对局编排不变。模型档案多一种「外部 agent」(网页上选,不写进 `config.yaml`):`complete()` 不发请求,而是把这一轮要交给模型的新内容放进信箱(`llm/external.py`),等外部 agent 通过 MCP 取走并回答。界面决策、参数校验、重问、Trace、对局页都照旧。
- 工具:

| 工具 | 作用 |
|---|---|
| `rules` | 玩法和规则(即 8.5 的系统提示词);上下文被压缩后可以重读 |
| `start_run` | 开始对局(难度可选),等到第一个需要判断的局面后返回 |
| `wait` | 等下一个需要判断的局面 |
| `act` | 提交判断和操作(参数同 API 模式的 act 工具),执行后返回结果和下一个局面 |
| `status` / `stop_run` | 查状态、停止对局 |
| `hook` | 只给 Claude Code 插件的 hook 调用(见下面的 Claude Code 接入) |

- **长等待**:战斗、动画期间没有需要判断的局面。`wait` / `act` 最多等 `wait` 秒后返回「还在等待」,agent 再调 `wait`。默认 50 秒,低于常见客户端 60 秒的默认工具超时;客户端能调大工具超时的,在地址上带 `?wait=540` 这样的参数减少空转(每次空转都是一次模型调用)。
- **回合**:每个回合的第一条消息自带本局档案,agent 不需要记住之前的回合;回合内的后续消息是执行结果 + 新界面。和 API 模式的区别是对话留在 agent 工具里一直累积,靠它自己压缩上下文。
- **超时**:局面交出去后 15 分钟没有任何 MCP 调用,就当作模型要求暂停(pause),对局停下等人处理。
- **网页**:对局记录里照常有每轮交给模型的内容和模型在 act 里写的分析、操作。模型在两次工具调用之间写的文字和思考内容不经过本服务(agent 工具自己的界面里能看到,以后可以用 hook 或插件转发);token 用量记为 0。
- **安全**:`/mcp` 只接受 Host 为 IP 地址或 localhost 的请求(防 DNS 重绑定),和网页接口一样不带认证,局域网访问靠防火墙限制。
- **持续游玩**:agent 中途停下来时,用 agent 工具自己的续行机制(DSH 的 `/goal`,Claude Code 插件里的 Stop hook,Codex 的 Stop hook)。

**DSH 接入**(`integrations/dsh/`):DSH 的 MCP 客户端(`@deepseek-ai/dsh-mcp-client`)支持 Streamable HTTP,工具名为 `mcp__cwagent__<工具>`,服务说明(instructions)会加进系统提示词;默认工具超时 60 秒,由 `toolCallTimeoutMs` 调大。

**Claude Code 接入**(`integrations/claude-code/`,仓库根目录的 `.claude-plugin/marketplace.json` 把它发布成插件市场):做成插件,用户装一次、填一个 serve 地址(插件的 `userConfig`),不用自己写 MCP 和 hook 配置。

- MCP:`.mcp.json` 连 `<地址>/mcp?wait=100`,`alwaysLoad` 让工具一开始就加载(不走工具搜索)。工具名是 `mcp__plugin_cwagent_cwagent__<工具>`。
- `wait=100`:Claude Code 主对话里超过 2 分钟的 MCP 调用会转成后台任务、模型先结束这一轮,和「一直等到下一个局面」的流程冲突,所以一次最多等 100 秒;HTTP 服务的空闲超时是 5 分钟,也够。
- `/cwagent:play [难度]`(skill):写明下棋流程;`allowed-tools` 免去 6 个工具的逐次确认(只在这一轮有效,用户插话后要重新确认,或在权限设置里永久允许)。
- 续行:skill 的 frontmatter 里带两个 `mcp_tool` 类型的 hook,只在调用过这个 skill 的会话里注册,serve 没开时也不会在别的会话里报错。它们通过插件已经连上的 MCP 服务调用 `hook` 工具(只给 hook 用),带上会话 ID:每次调用本服务的工具后(PostToolUse)记下「这一局是哪个会话在下」(新对局清空);想停下时(Stop),对局还在进行、且就是这个会话在下,就返回 `additionalContext` 让模型接着调 `wait`,否则放行。这样换一个会话接手、或者 DSH 在下时,之前下过的 Claude Code 会话不会被拉回来抢着下。连续续行次数由 Claude Code 限制(8 次,调用过工具就重新计数)。
  - 没用 `command` hook + `curl`:skill frontmatter 里的 hook 不替换插件的 `${user_config.*}`(2026-11-16 实测,curl 拿到的是原样的 `${user_config.server_url}`),放到插件级 `hooks/hooks.json` 又会在所有会话里生效。
- 没有用 Claude Code 自带的 `/goal`:它每次停下都要再问一次模型判断条件,而对局是否结束 serve 自己知道。

## 12. Trace、回放与评测

### 12.1 Trace

`runs/<时间戳>_<档案名>/`:

- `meta.json`:模型档案(不含 key)、配置快照、赛季版本、难度、开始 / 结束时间、结果;
- `steps.jsonl`:每个循环步一条:

```json
{"step": 37, "ts": "…", "screen": "prepare", "shot": "shots/0037.jpg",
 "state": {…GameState…},
 "decision": {"layer": "tactical", "profile": "opus",
              "system": "…", "user": "…",
              "response": {"text": "…", "reasoning": "…", "tool_calls": […], "usage": {…}, "latency_s": 4.2},
              "validation": {"ok": true, "errors": [], "retries": 0}},
 "actions": [{"op": "buy", "args": {"slot": 0}, "reason": "…", "result": "ok"}]}
```

- `shots/`:每步截图(JPEG);`debug/`:异常时的原图。
- `vision/`(2026-11-16,第 20.3 节):每次发给模型的那张带标号的图,离线回放时原样发给别的模型。
- `pending.json`(2026-11-18):模型决策中的那一步。开始问模型时就写(步号、界面、节点、模型看的标号图),流式收到的
  思考(只留最后 12000 字)和从工具参数里取出的写到一半的判断最多每 0.25 秒更新一次;没有片段时每 20 秒心跳刷新,
  对局列表据此判断对局还在进行(原来只看 `steps.jsonl` 90 秒内有没有写入,模型想得久就被当成结束了)。决策结束后删掉;
  这一步的完整记录(含完整思考)照旧在程序执行完操作后写进 `steps.jsonl`。用文件而不是进程内状态,命令行启动的对局也能看。
- `report.md`(2026-11-16,第 20.9 节):整局结束时生成的逐节点报表,`cwagent runs report <对局>` 也能对旧对局重算。

反射层的步骤也记录(`decision` 为空),这样回放是完整的。

### 12.2 离线回放与模型对比

`cwagent replay <run> --models A,B [--steps 10-40]`:取历史对局中的决策步,用同样的 `system` / `user` 调用其他模型,结果存到 `runs/<run>/replays/<档案名>.jsonl`。只比较"同一局面下各模型会怎么做",不执行动作。前端模型对比页读这些文件并排展示。

### 12.3 实机评测

固定模式和难度,每个模型跑 N 局。指标:通关率、到达的最远阶段、剩余生命、非法动作率、重问次数、每局调用次数 / token / 耗时 / 估算费用。商店和事件随机性大,少量对局只能看趋势,报表里要显示样本量。

### 13.1 实时画面(2026-11-14 已在 Windows 实机验证)

对局页显示游戏的实时画面,局域网内 1080p60。agent 自己的截图走 6.1,和这条链路互不相干。

```
ffmpeg gfxcapture(Windows Graphics Capture,按 StarRail.exe 抓窗口;窗口被挡住也能抓,不能最小化)
  → 显存里的 BGRA 帧直接给硬件编码器(h264_nvenc / h264_amf;都不可用时 hwdownload 后 libx264)
  → RTSP 127.0.0.1:8554 → MediaMTX → WebRTC(媒体走 UDP 8189)→ 浏览器 <video>
```

- **按需**:MediaMTX 有观众时才拉起 ffmpeg(`runOnDemand`),最后一个观众离开 15 秒后停止;页面切到后台时前端主动断开。
- **只开一个口**:MediaMTX 的 HTTP 和 RTSP 都只监听本机,浏览器的 WHEP 信令经后端转发;对局域网只开放 UDP 8189(防火墙规则按 `mediamtx.exe` 路径放行,限本地子网)。
- **安装**:ffmpeg(BtbN 8.1 GPL 构建,8.1 起才有 gfxcapture)和 MediaMTX(固定 v1.21.3,它的配置遇到不认识的字段会报错)不随仓库分发。`cwagent serve` 启动时缺少就在后台下载到 `data/tools/`,管理员身份下先加防火墙规则再启动(否则第一次监听端口会弹防火墙提示,被取消后系统会建优先级更高的阻止规则);`cwagent stream setup` 手动重装;README 写明手动安装步骤。
- **进程**:MediaMTX 绑在 Windows 作业对象上(`KILL_ON_JOB_CLOSE`),serve 被强制结束时它和 ffmpeg 一起退出。
- **编码参数**:不用 B 帧(WebRTC 不支持),关键帧间隔 2 秒,CBR 20 Mbps(`config.yaml` 的 `stream` 段可调帧率、码率、编码器)。NVENC 收 RGB 输入时自行转 YUV 并在码流里标 BT.601 有限范围,浏览器显示颜色正确;`scale_d3d11` 在这台机器上建纹理失败,不用。
- **实测**(RTX 5060 Ti,Windows 和 Mac 都走 Wi-Fi):经后端转发的完整链路收到 1920x1080、约 60fps,丢包 0,首帧 1.5–2.5 秒(含拉起 ffmpeg)。端到端延迟没有测。AMF 和 libx264 两条路径没有实机验证。

## 16. 开发工作流

1. **任意平台可完成并自测**:知识同步(接口可直连)、标记清洗、模板库、LLM 接入层、决策层(对手写的 GameState 和 fixtures)、离线回放、后端接口、前端全部页面、感知层算法(对 fixtures)。
2. **必须在 Windows 上**:截图与键鼠、`collect` 采集、执行层联调、实机对局。在其他电脑上开发时,推送后在 Windows 上 `git pull`,再通过 SSH 运行。
3. **SSH 会话看不到用户桌面**:在 SSH 里直接启动的进程截图是黑的、键鼠无效。需要接触游戏的进程(agent 服务、采集工具)要启动到用户已登录的桌面会话里,例如用计划任务(`schtasks /Create ... /IT /RL HIGHEST` 后 `schtasks /Run`)。之后通过 agent 后端接口、日志文件和 `runs/` 目录观察与调试。
4. 每个依赖 Windows 的功能都要有不依赖 Windows 的测试路径:截图源可替换为"从目录读图片",输入设备可替换为"只记录不执行"的假实现。用这两个替身可以在任何平台上把整条主循环对着一组 fixtures 跑通。
5. 报告进度时如实区分"已在非 Windows 平台验证"和"已在 Windows 实机验证"。

## 20. 2026-11-16 优化方案

依据:Windows 上 2026-11-14 ~ 16 的 42 个对局目录(deepseek-flash、外部 agent、gpt-6.1-sol),trail-cli 源码,
以及几个公开游戏 agent 的 harness(Claude Plays Pokémon、Gemini Plays Pokémon、BalatroLLM、Voyager)。本节与前文冲突时以本节为准。
任务拆分和进度在 `docs/TODO.md`。

### 20.1 诊断

**结果**:42 个对局目录没有一局打完(stopped / max_steps / pause),胜率还量不出来。第一位面除奖励节点外的战斗大多输了,
1-3、1-4 的进度只有 10%~66%,到 1-9 血量剩 31~46。最近几局是 A8-20(敌人难度 89),不是约定的 A8-1(67)。

**阵容太弱**:

| 问题 | 证据 |
|---|---|
| 有钱不花 | 一局只买 3~12 次角色、刷新 1~3 次、买经验 1~3 次;1-9 时 44~56 金币、6 级,有一局 2-4 时 74 金币还是 6 级;小结里反复「不刷新不升级」「不付 3 金盲刷」 |
| 前台只站一人 | 有一局整个第一位面前台只有银狼,上场名额全给了后台;另外两局也一样 |
| 全是 1 星 | 到 1-9 场上几乎全是 1 星,同名两张差一张也没人去刷 |
| 看不到商店 | 有一局 32 轮备战里 23 轮没读到商店,另一局 36 轮里 19 轮 |
| 道具从没用过 | 23 条投资策略、2 个投资环境会发扳手、投影仪、冶金炉等,没有对应操作 |

**程序缺陷**:按节点类型触发的记忆(「前台站满」「奖励节点规则」)从没注入过,因为组装提示词时没传节点类型;
「人数未达上限」时程序勾「本局不再提示」后确认;买经验升级后程序缓存的上场人数没更新,拦下了模型的上场;
投资环境、战斗结算被错判成备战界面。

**循环**:有一局备战回合里坐标 / 文字点击 41 个、买卖站位 39 个,大半在替程序收拾界面(没打开的商店、被缓存挡住的上场、
被商店挡住的出战和「选择主角」);刷新一次就停下算一轮,出战又单独一轮;方向每回合重新权衡。

**输入**:备战回合开场平均 1.18 万字,其中条目说明 2652、操作说明 1228、候选攻略 873、相关经验 640 字每回合重复;
「主 C / 辅助」的说法在系统提示词、操作说明、规则卡、记忆里共 22 处;规则卡只讲利息,攻略标签「速升8级」被理解成攒钱;
真正要的事实(羁绊档位、同名张数、前台人数、多出来没有利息的金币)没有。

### 20.2 原则

1. 模型看截图为主,OCR 和程序为辅;只接入能看图的模型。
2. 程序负责界面,模型负责决策;界面出问题由程序重试,还不行就暂停,不占模型的轮数。
3. 程序只给事实,不给建议;打法原则集中一处,由维护者审定。
4. 输入分块,只在出现新内容时追加,不重复。
5. 方向在检查点定,备战回合只执行。
6. 先在 A8-1 拿到可量化的基线,再调策略。

参考做法:Claude Plays Pokémon 每次操作返回截图 + 从内存读出的位置、背包等(比看图可靠),知识库由模型自己用工具增删改,
教训是模型看错图会把错的事实写进知识库;Gemini Plays Pokémon 在截图上叠网格,程序维护文字版小地图,开发者「从不给具体提示」;
BalatroLLM 把打法说明(静态)、当前局面、最近 10 个操作和上次错误分成固定模板,不需要判断的界面不交给模型;
trail-cli 围绕一篇固定攻略整理事实,人数没满时拦下出战,用请求日志和「过期」标记保证状态可信。

### 20.3 多模态感知

- **分工**:模型看截图判断界面是什么、局面长什么样、上一步有没有生效;程序继续负责界面分类与规则处理(不调模型)、
  读小数字(金币、血量、等级、经验,视觉模型容易读错)、名字链接知识库、局面要点(20.4)、标号坐标、战斗监视。
  截图和程序读到的事实冲突时以截图为准。
- **标号**:程序在截图上画编号。备战界面标格子(前 1~4、后 1~9、备 1~9、商店 1~5、装备栏、道具栏),`buy`、`move` 等语义操作不变,
  模型能在图上核对编号;其他界面给 OCR 文字和模板认出的图标(右上角 X、箭头等)编号,`click` 用 `mark=N`,`x`、`y` 坐标留作兜底。
  视觉模型直接报像素坐标不准,所以按标号操作(Gemini Plays Pokémon 的网格是同一个思路)。
- **规格**:客户区截图缩成 1280x720 JPEG(Anthropic 估算每张约 1.2k token);`zoom(区域)` 返回原分辨率局部图。
  图只留在当前回合的对话里,回合结束后本局经历只留文字。
- **纠错回路**:act 增加可选字段 `perception_issues`,模型指出程序认错的地方,记进对局记录,用来改感知。
- **记录**:每次发给模型的图存进 `runs/<id>/vision/`,离线回放原样重发,网页按步骤显示。
- **外部 agent**:MCP 的返回带上图片内容(另一个会话在做 Claude Code 接入,图片部分等那边合入后再做;DSH 能否传图待验证)。

### 20.4 输入分块

| 块 | 谁写 | 什么时候变 | 内容 |
|---|---|---|---|
| 系统提示词 | 维护者 | 整局不变 | 玩法、操作和标号说明、规则卡、打法原则 |
| 整局已知事实 | 只有程序 | 出现新事实时追加一条 | 难度、首领、奇遇伙伴及效果、投资环境原文;每个位面的节点序列和敌人词条;已拿的投资策略、主角光环;持有的道具;改变经济的修正(如「融资危机」刷新 3 金) |
| 条目说明 | 程序 | 档案里留全;每个回合开场按当前局面挑(2026-11-18) | 当前相关的官方描述:界面上的角色、装备、投资(场上、备战席、商店、选项)、场上和备战席角色的羁绊、选的投资环境、拿到的投资策略、主角光环、身上的装备和道具、笔记里提到的。羁绊跟着角色走,商店卡面上的羁绊标签不带 |
| 想起的经验 | 程序 | 档案里留全;每个回合开场重新判断(2026-11-18) | 战略检查点从全部记忆检索,其他回合只在这局想起过的里按当前局面(选的环境和投资、阵容、当前和下一个节点)筛;不再适用的退出 |
| 本局经历 | 程序记录 + 模型的回合小结 | 每回合追加一行 | 去掉坐标等程序细节 |
| 我的笔记 | 只有模型 | 模型想改时整体改写 | 方向、主 C、经济计划、待办(现在的 `run_notes` 升级成分节笔记) |
| 当前回合 | 程序 | 每轮 | 带标号的截图、程序读到的数字和格子、局面要点;回合内后续轮只给执行结果和变化 |

- 事实块和模型笔记分开:模型发现事实不对时用 `perception_issues` 指出,程序核对后改。
- 随时会变的状态(当前血量、「轮岗」本阶段翻倍的费用)放在当前回合,不进事实块。
- 不再每轮发:操作说明(移进系统提示词)、整屏 OCR 列表、候选攻略、程序的催促话
  (「最近 3 步画面没变」「第 N 次进入备战」)。操作没生效只在执行结果里如实报告。
- 回合开场的顺序:本局经历、整局已知事实、条目说明、想起的经验、当前状态、当前回合。经历只往后加,放最前面,
  新增事实不打断它。
- 本局经历保留全部回合(维护者要求),事实和条目说明分出去后整局约 6~9k 字;以后太长再按位面折叠成小结。
  只记关键的:购买、升级、装备变化、没成功的操作、战斗结果、模型小结;「这一轮没有出战,出战要单独一轮」这类
  当轮反馈只留在执行结果里。
- API 每个回合是新对话,开场带上当前相关的条目;回合中途又出现、这段对话里还没说明过的条目随执行结果补上。
  外部 agent 保留整局对话:只交付新增的经历和事实、还没收到过的当前相关条目;适用的经验变了就整组交付,
  并说明之前给过、这次没列出的不再适用(它收到过的不会因为服务端换了列表就消失)。
- 性能监控叠加层(最上面一行 FPS / CPU / GPU / 显存)整行不算界面文字。

**攻略卡片**(2026-11-16 已做):官方攻略没有逐节点的流程,能拿到的是作者思路(官方上限 200 字,列表和详情接口一样;
有的作者在里面写了逐节点打法)、前期 / 中期 / 最终三个阶段的阵容(前中期只有角色、星级、前后台和羁绊人数,没有装备)、
最终阵容的装备、次选装备、推荐光环、装备顺序和两组推荐投资策略。卡片全部给出,作者原文不截断;入库格式变了以后用
`cwagent knowledge rebuild` 从库里存的接口原始响应重建,不必再请求接口。

**局面要点**(程序算的事实,放在当前回合):
- 经济:下个节点的利息、超过 50 不产生利息的金币、刷新价(从界面读)、升下一级还要买几次经验;
- 升星:场上 + 备战席每个角色有几张;商店里哪一格买了就升星;
- 羁绊:「连击 2*,4,6(当前 3 人)」,`*` 是已激活档位(trail-cli 的格式);
- 站位:前台 x/4、上场 a/b、还空几个名额;
- 相对当前方向:商店卡是不是方向里的角色;备战席角色属于前期过渡、后期核心还是无关;
- 道具:每个道具现在能用在谁身上;
- 战后:本局经历里写一行出战时的客观异常(前台人数、1 星比例、闲置金币、上场没满),不调模型。

### 20.5 循环与检查点

- **程序包办界面**:开关商店和面板、首领节点的「选择主角」入口、晶矿、查看道具、执行核对。
- **战略检查点**:选投资环境时、每个位面读完词条和节点后、首领前、连输两场或血量跌破阈值、拿到会改变流程的修正后。
  只在这里给攻略候选、检索新的相关经验,模型据此改写自己的笔记。攻略默认固定一篇,检查点才比较、改选。
- **备战回合**:模型一次给出一组操作(可以用宏),程序执行并核对。`ready` 可以和其他操作一起发:程序检查人数和站位,
  没问题直接出战,有异常才停下报告。轮数上限只作安全阀(约 10 轮),刷新不再打断回合。预计每个节点 1~2 次调用。
- **没见过的界面**:模型看标号操作,仍然卡住就暂停交给人,不在坐标上反复试。
- **选择界面**(投资策略、补给、遭遇等)不变。

### 20.6 新增操作

| 操作 | 作用 |
|---|---|
| `roll(targets, until, keep_gold, max_refresh)` | **2026-11-18 已做**(维护者:极端时要刷十几二十次,一次刷新一轮决策不合理)。程序反复「买下商店里的目标 → 刷新」:targets 每项是角色名加要凑到的星级(场上和备战席已有的按一星的量算,二星 3 张、三星 9 张;商店里按价格判断的二星卡算 3 张)或这次买几张;until 是全部 / 任意一个达成才停;keep_gold 保底金币(买卡、刷新都不低于它);max_refresh 默认 10、最多 30。备战席满了买不进、刷新没生效(卡没变且金币没扣)、商店被收起也停。结果(刷新次数、花费、买到什么、为什么停、现在金币、每个目标的进度)交给模型,同一轮后面的操作不执行 |

### 20.7 道具栏(消耗品)

机制和来源见 `docs/TODO.md` 的道具栏条目。道具正好对得上 20.1 的毛病:投影仪复制角色(解决全是 1 星)、扳手换主 C 时挪装备、
特权赋予卡让关键装备翻倍、冶金炉重掷、好运令牌拿主 C 的推荐装备。做法:

- 坐标先借 M7A 的道具栏区域,实机校准后标号;
- 新道具第一次出现时程序点开读名字,存下图标,以后直接认(和认不出的角色卡点开看详情同一套);数量由模型看图、程序 OCR 对照;
- `use_item` 执行后核对:数量减少;投影仪要多出复制品;扳手要让装备回到装备栏;好运令牌、特权赋予卡用完后的弹窗留在同一回合,
  模型看图点标号;
- 局面要点列出每个道具能用在谁身上;规则卡补道具表。前提是 Windows 上的道具栏截图。

### 20.8 规则卡、打法原则、记忆

- 规则卡只写核实过的规则;打法原则单独一段、只放一处(「主 C」从 22 处减到 1 处);面向模型的部分去掉已由程序处理的坐标和关面板方法。
- 补齐:前台和后台在战斗里的分工(只有前台挨打)、输一场扣多少血、输了没有任何收益(两者维护者 2026-11-16 确认)、超过 50 的金币没有利息;
  攻略节奏标签「速升8级」「5级搜牌」的含义(不是让人攒钱)。
- 维护者关于怪物词条影响的说明(「第一位面强化」要多投经济在过渡阵容;「忍无可忍」要多上生存位和生存装备)整理成记忆。
- 记忆的线索要带当前和下一个节点的类型;记忆在检查点按事实触发,不每回合重复注入。

### 20.9 评测与报表

- 难度回到 A8-1,固定一个模型,先跑通 3~5 整局拿基线;之后每个阶段做完都在 A8-1 跑几局对比。
- 每局生成逐节点报表(`runs/<id>/report.md`,`cwagent runs report` 可对旧对局重算):节点、进场血量、金币、等级、上场、
  前台人数、2 星及以上张数、战斗进度与胜负、模型调用次数和输入 token。
- 统计 `perception_issues`;之后做 5.4 节的局后复盘。
